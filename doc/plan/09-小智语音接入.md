## 1. 结论先行

| 问题 | 结论 |
| --- | --- |
| 要不要插内存卡（TF/SD）？ | **不需要**。本项目已有 7.875 MB SPIFFS 分区，网页资源只占几十 KB，语音 assets（唤醒词模型、提示音）放 SPIFFS 即可。且本板 `codec_board/board_cfg.txt` 的 `S3_RLCD_4_2` **没有 sdcard 配置段**，硬件上大概率也没有卡槽，不要再为此改板。 |
| 需要多大空间？ | 融合小智后 app 固件预计 **3.5 ~ 4.5 MB**，现有 `ota_0/ota_1` 各 4 MB **太紧**，建议扩到 6 MB（见 §4）。 |
| 是否只能语音？ | 不是。小智支持 **MCP 协议**，可以把「翻月 / 刷新天气 / 同步 RaceBox」注册成工具，服务端识别意图后回调设备执行，屏幕同步切换。 |
| 推荐方案 | **方案 A：同板融合**（见 §3）。喇叭已接在本板，不要再加一块协处理器。 |

## 2. 现状盘点

| 项目 | 现状 |
| --- | --- |
| MCU | ESP32-S3，16 MB Flash，Octal PSRAM（80 MHz，8 MB），CPU 160 MHz |
| 音频 | `codec_board` 已跑通：`S3_RLCD_4_2` → ES8311 输出（PA GPIO46）/ ES7210 输入，`audio_service_beep()` 已验证喇叭有声 |
| 显示 | 400×300 单色 RLCD，LVGL 8.4，双全屏帧缓冲在 PSRAM，单屏 `main_screen` |
| 网络 | Wi-Fi STA/AP、HTTP 服务、MQTT、BLE（NimBLE，RaceBox） |
| 分区 | `nvs 24K / otadata 8K / phy 4K / ota_0 4M / ota_1 4M / spiffs 7.875M` |

### 小智（xiaozhi-esp32）需要什么

- ESP32-S3 + ≥8 MB PSRAM（满足）+ ≥8 MB Flash（满足）
- 麦克风 + 功放（满足：ES7210/ES8311）
- 服务端：WebSocket（或 MQTT+UDP）协议；MCP 用于设备控制
- 音频链路：ESP-SR 唤醒（WakeNet）+ Opus 编解码 + AEC/AGC/NS

## 3. 三种方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **A 同板融合** | 把 xiaozhi-esp32 的 `application` / `protocol` / `audio_processor` / `mcp_server` 移植进本工程，共享同一个 LVGL 与配置系统 | 一套配置、一套 UI、语音可直接操作所有模块 | 工作量最大；flash/RAM 紧张需优化 | ✅ 推荐 |
| B 协处理器 | 再加一块 ESP32 跑原版小智，通过 UART/MQTT 给本板发指令 | 不动现有固件、风险低 | 喇叭已接本板，等于要拆/改线；多一处配置、多一套 OTA | ❌ 不推荐 |
| C 双固件切换 | 同一块板刷两套固件按需切换 | 看似省钱 | RLCD/LVGL 与小智 UI 冲突，切换必重启，语音无法控制日历 | ❌ 不可行 |

## 4. 空间预算与分区调整

### 4.1 Flash 预算（16 MB）

| 内容 | 估算 |
| --- | --- |
| 现有固件（LVGL + RLCD + NimBLE + MQTT + HTTP + cJSON + 中文点阵字库） | **实测 1.71 MB**（`deskwong.bin 0x1a20b0`，占 4 MB 分区 41%，剩 59%） |
| 小智增量：ESP-SR（WakeNet 唤醒 + 命令词） | 0.8 ~ 1.2 MB |
| Opus 编解码 + 音频处理（AEC/AGC/NS） | 0.3 ~ 0.5 MB |
| WebSocket/MQTT+UDP 协议 + MCP 客户端 + 状态机 | 0.3 ~ 0.5 MB |
| 语音相关 UI（表情/状态条/滚动字幕） | 0.1 MB |
| **融合后 app 合计** | **3.4 ~ 4.2 MB**（实测基线 1.71 MB，仍有余量） |
| SPIFFS：网页 `dist`（~40 KB）+ 唤醒词模型/提示音 | ≤ 2 MB |

> 建议：把唤醒词模型、提示音、大字体全部放 SPIFFS，代码里按需加载，可再省 0.5~1 MB flash。

### 4.2 分区要不要改？

**结论：先不改。** 实测当前固件只有 1.71 MB，4 MB 的 app 分区还有 59% 空余；
加上小智增量后预计 3.4~4.2 MB，**大概率仍然塞得下**。等 V3 阶段实测溢出后再调整。

若确实溢出，用下面这套（app 各 6 MB，spiffs 3.875 MB）：

```csv
# Name,    Type, SubType, Offset,   Size,      Flags
nvs,       data, nvs,     0x9000,   0x6000,
otadata,   data, ota,     0xf000,   0x2000,
phy_init,  data, phy,     0x11000,  0x1000,
ota_0,     app,  ota_0,   0x20000,  0x600000,
ota_1,     app,  ota_1,   0x620000, 0x600000,
spiffs,    data, spiffs,  0xC20000, 0x3E0000,
```

- `ota_0/ota_1` 各 **6 MB**（0x600000），给融合固件留 1.5 MB 余量；
- `spiffs` **3.875 MB**，放网页 + 语音 assets 绰绰有余；
- 起始偏移 `0x20000` 与现有保持一致，OTA 滚动升级不受影响。

### 4.3 RAM / PSRAM

| 项 | 估算 |
| --- | --- |
| LVGL 双帧缓冲（已放 PSRAM） | ~0.5 MB |
| Opus + 音频环形缓冲（16 kHz/16 bit/单声道） | 60 ~ 120 KB |
| ESP-SR 模型运行时 | 200 ~ 400 KB（放 PSRAM） |
| WebSocket/MQTT 收发缓冲 | 30 ~ 60 KB |

8 MB PSRAM 足够，但需要：
- 打开 `CONFIG_SPIRAM_USE_MALLOC` / `SPIRAM_TRY`，把 `LV_MEM_POOL`、音频缓冲、Opus 堆全部指向 PSRAM；
- 内部 RAM 留给 Wi-Fi/BLE 共存与协议栈，注意 BLE（RaceBox）与 Wi-Fi（语音上行）同时跑时的共存配置。

## 6. 语音指令 ↔ 设备动作（MCP 工具）

在设备侧注册 MCP 工具，服务端做意图识别后回调：

| 用户说 | MCP 工具 | 设备动作 | 屏幕表现 |
| --- | --- | --- | --- |
| 「下个月 / 上个月」 | `calendar.turn_month(+1/-1)` | 重算并刷新月历 | 主屏翻月 |
| 「回到本月」 | `calendar.today()` | 回到当前月 | 主屏 |
| 「刷新天气」 | `data.refresh(weather)` | `net_scheduler_request(NET_JOB_WEATHER)` | 天气区闪一下，显示「更新中」 |
| 「刷新 AI 额度」 | `data.refresh(ai)` | `net_scheduler_request(NET_JOB_AIUSAGE)` | 右侧额度条刷新 |
| 「刷新工时」 | `data.refresh(worktime)` | `net_scheduler_request(NET_JOB_WORKTIME)` | 月历工时进度条刷新 |
| 「全部刷新」 | `data.refresh(all)` | 三个任务依次**入队**（不并发） | 状态栏「刷新 1/3」 |
| 「同步 RaceBox」 | `racebox.sync()` | `racebox_service_trigger()` | 弹出同步窗：搜索 → 连接 → 进度 → 总条数 |
| 「今天几号 / 农历多少 / 哪天放假」 | `calendar.query(what)` | 本地计算 | 底部文字条回答 |
| 「室内多少度」 | `sensor.indoor()` | 读 SHTC3 | 底部文字条回答 |
| 「还有多少额度」 | `data.ai_summary()` | 读缓存的 AI 用量 | 底部文字条 + 额度条高亮 |
| 闲聊/问话 | 云端 LLM | TTS 播报 | 底部滚动字幕 |

> 关键约束：所有刷新类指令**必须走 `net_scheduler` 排队**，不要直接调用 `*_service_fetch()`，
> 否则会和定时拉取抢 `http_util` 的共享缓冲（见 `03-配置后台.md` §调度）。

## 7. 屏幕状态联动

新增一个轻量语音状态条（复用 `main_screen` 底部区域，不新增整屏）：

| 状态 | 显示 |
| --- | --- |
| 空闲 | 现有底部提醒条 |
| 聆听中 | 麦克风图标 + 「聆听中…」 |
| 思考中 | 「思考中…」+ 呼吸点 |
| 回答中 | 滚动字幕显示回答文本 |
| 执行工具 | 显示工具名，如「正在同步 RaceBox」；完成后自动回到空闲 |

唤醒/执行期间**不要**整屏切换：RLCD 是反射屏，全屏刷新慢且有残影，局部刷新即可。

## 9. 风险与注意

1. **flash 紧张**：先做 V1 分区调整再移植，否则 4 MB app 分区一定溢出。
2. **AEC 必须开**：喇叭与麦克风在同一块板上，不开回声消除会自激啸叫。
3. **Wi-Fi + BLE 共存**：语音上行（Wi-Fi）与 RaceBox 采集（BLE）同时跑，需要打开 `CONFIG_ESP32_WIFI_SW_COEXIST_ENABLE` 并降低 BLE 扫描窗口。
4. **唤醒词模型放 SPIFFS**：避免挤占 app 分区。
5. **服务端**：小智需要自建 `xiaozhi-server`（Docker 一键部署）或使用官方服务；MCP 工具需在服务端注册同名工具。
6. **功耗与发热**：4.2 寸反射屏本身不耗电，但 S3 长时间音频编解码会发热，注意外壳散热。
7. **隐私**：录音只在唤醒后上传，配置页需提供「录音开关」并在 `/api/system/logs` 中脱敏。
